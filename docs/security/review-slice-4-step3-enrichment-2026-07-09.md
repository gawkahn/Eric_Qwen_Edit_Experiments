# Security Review — Slice 4 Step 3: `extract_params` catalog-DB enrichment

**AI-Disclosure:** Claude (Opus 4.8, 1M context) authored this security review; Grant to review. L3 Red Zone (LLM-agent MCP surface, ADR-022 S5 metadata plane surfacing untrusted civitai-sourced text).
**Date:** 2026-07-09
**Reviewers:** `security-auditor` (Opus) + `code-reviewer` (Opus), both per the project CLAUDE.md review bar.
**Change under review:** new `_enrich_from_catalog_db(names, catalog, db_path)` + its wiring into `_handle_extract_params` (top-level `enrichment` key) in `comfyless/mcp_server.py`. Prior related reviews: `docs/security/review-slice-4-mcp-extract-params-2026-07-07.md` (step-4 core); `search` tool is ADR-022 S5.
**Verdict:** **CLEAN at CRITICAL/HIGH/MEDIUM** (security-auditor); **APPROVED** (code-reviewer). Fold-ins applied before commit; residual INFOs accepted at the threat model.

## Threat model
Single-user desktop; same-uid LLM agent over stdio. The metadata DB is the user's own, built offline; `description`/`usage_tips`/`trigger_words` originate from the public web (civitai) and are UNTRUSTED prompt-injection DATA. Boundaries defended: (a) no server-side filesystem path (`abs_path`/`root`/`relative_path`) crosses to the agent; (b) untrusted text egress must be equivalent to the already-reviewed `search` tool (same fields, same storage-time sanitize, same read-boundary guard, same DATA framing); (c) enrichment is read-only, post-resolution, hits-only, fail-open, and never influences the load/resolution plane.

## What was verified (security-auditor, CLEAN)
1. **Untrusted-text parity.** Enrichment projects the identical field set as `_handle_search` (`source, model_name, description→text, usage_tips, strength_rec, sampler_rec, trigger_words`). `trigger_words` is re-validated on read exactly as `_handle_search` does (`json.loads` → `isinstance(list)` → `[str(w)[:64] for w in parsed if isinstance(w, str)][:64]`), so a DB written outside the sanitizing path cannot emit nested structures or oversized payloads. The tool description carries the DATA-not-instructions framing and "No path-typed fields ever appear." Enrichment discloses a strict subset of `search`.
2. **No path egress.** `catalog_db.search` returns `SELECT e.*` (carrying `abs_path`/`root`/`relative_path`), but `_enrich_from_catalog_db` builds a fresh `meta` dict by explicitly picking `classification`, `model_family`, and a whitelisted description block — never `dict(row)`. The path columns present on the row are never referenced. Confirmed by code-reviewer too (focus 2).
3. **Load/resolution-plane independence (ADR-022).** Enrichment runs after `_render_extracted_params` completes resolution against the live `cfg.catalog`; keyed by resolved `hit_names`; opens the DB `mode=ro`; no model load, no write, no influence on name selection.
4. **Fail-open + connection lifecycle.** `not db_path or not names → {}`; `connect_readonly` wrapped `(CatalogDBError, sqlite3.Error, OSError, ValueError) → {}`; per-name `(sqlite3.Error, ValueError) → continue`; `conn.close()` in `finally`; `db_path` is the server-controlled, startup-realpath'd `cfg.catalog_db_path`.
5. **Hits-only, no probe oracle.** `_record` adds to `hits` only in the `elif name in catalog` branch; misses (basename fallback) and HF-repo passthroughs are never enriched, so an agent-supplied arbitrary basename that misses the catalog yields no enrichment and cannot probe DB contents. Any name that does enrich is already discoverable via `list_*`/`search`. `db_search(..., kind=kind, limit=25)` is filtered to the exact `name` (unique per `(kind, name)`).
6. **SQL injection / exact-name resolution.** `catalog_db.search` binds all parameters and quotes the FTS term. Code-reviewer confirmed the exact-name row (a `name LIKE 'name%'` prefix hit, `rank_class 0`) always sorts ahead of FTS/substring rows; being pushed past `limit=25` would require 25+ same-kind entries literally prefixed by the full name (pathological) and fails open.

## Findings & resolutions

- **[security INFO-3 / code-reviewer LOW-1] "never crash" was analytical, not structural — FOLDED.** An unexpected (non-`sqlite3.Error`/`ValueError`) exception mid-enrichment would have propagated and lost the already-computed `params`. Resolved by wrapping the enrichment call in `_handle_extract_params` with a top-level `try/except Exception → enrichment = {}` (logging only `type(e).__name__` to stderr — no path/agent data), making the invariant-12 "enrichment degrades, never fails the call" a STRUCTURAL guarantee. New test `N-guard` monkeypatches the helper to raise and asserts `params` is still returned with no `enrichment` key.
- **[code-reviewer LOW-2] connect `except` omitted `ValueError` — FOLDED.** Added `ValueError` to the `connect_readonly` except tuple for symmetry with `_discover_default_catalog_db` (unreachable for the startup-validated path; defense in depth).
- **[code-reviewer INFO test gaps] — FOLDED.** Added a `classification` to the fixture + assertion, and a top-level `model_family` enrichment assertion (N17).
- **[security INFO-1] read-side text fields emitted verbatim (only `trigger_words` re-guarded) — ACCEPTED.** Exact parity with `_handle_search`; storage-time caps (4096/2048/256/128) apply; fields framed as untrusted DATA; DB is the user's own. If ever hardened, apply matching `[:CAP]` slices in both `_enrich_from_catalog_db` and `_handle_search` together.
- **[security INFO-2] per-name enrichment cost scales with sidecar LoRA count — ACCEPTED.** Self-DoS on the user's own file, same posture as the accepted unbounded `json.load` (step-4 core review).

## Verdict
**CLEAN at CRITICAL/HIGH/MEDIUM + APPROVED.** The enrichment surface is a provable subset of the already-reviewed `search` tool; `SELECT e.*` path columns are never projected; enrichment is post-resolution, hits-only, read-only, and now structurally fail-open. Fold-ins applied; residual INFOs are parity/self-DoS items accepted at the single-user threat model.
